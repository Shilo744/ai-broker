# AI Broker - design (one page)

**What:** one background service (the *broker*) that every agent uses to start local AI/GPU jobs (ComfyUI Qwen/Z-Image, TripoSG, Step1X-3D, Blender, ACE-Step/MOSS, hidden Godot runs), plus a desktop GUI and a CLI that are only *clients*. Closing the window or the terminal never stops the queue.

**Why:** 2026-11-09, 22 TripoSG shapes + Step1X + Qwen + Blender at once -> commit 109 GB, RAM 100 %, SSD 100 %, PC stuttering. The fix is not "one job at a time" but "as many as fit".

## Limits (soft, editable while running)
`config.json` (also GUI sliders and `aijob limits`): `ram_gb` (budget for the sum of running jobs, default 46 of 64), `vram_gb` (default 14 of 16), `max_jobs` (4), `reserve_ram_gb` (6, must stay free after a start), `min_commit_free_gb` (20). Safety brake: free RAM < `hard_free_ram_gb` (2.5) or free commit < 8 GB => no starts, and the youngest running job is *suspended* (not killed) until memory recovers.

## Job spec
A job = `type` + params + requester. Types live in `jobtypes/*.json` (title, group, class gpu/cpu, `model` key for affinity, `est` {ram, vram, commit}, `max_parallel`, `params` with defaults, `cmd` template, env). `aijob submit <type> k=v ...` resolves the command at submit time and stores it. `custom` type = any command after `--` with explicit estimates. Estimates: spec override > **learned** (90th percentile of the last 10 successful runs of the same `est_key`, x1.1, from History) > type default (flagged "default" in the queue until measured).

## Scheduling rule (every second)
Walk the queue in order. Start a job when ALL hold: not paused / not "playing" (GPU jobs) / dependency done; sum(running RAM) + job <= `ram_gb` (running = max(estimate, live working set)); same for VRAM (+ whatever other programs, e.g. the game, already use: measured, not guessed); running < `max_jobs`; type `max_parallel`; free RAM and commit after the job's still-unloaded part >= reserve; no foreign GPU lock. Jobs that do not fit are skipped (backfill: a small Blender run slips past a waiting Qwen) unless the head of the queue has waited 15 min - then nothing overtakes it.
**Affinity:** jobs whose `model` is already loaded (running, or finished < 3 min ago) are lifted ahead of other-model jobs inside the first 8 queue slots, never past a job the owner moved by hand (those are "pinned"). Real model reuse needs batch jobs (one process, many items): the Qwen and TripoSG runners accept a list.
**Legacy lock:** the broker holds `.../3D maker/characters/.gpu.lock` while any GPU job runs (so char_forge / old scripts wait) and does not start GPU jobs while a foreign holder has it. Godot visual runs take the lock themselves (`self_lock`).

## Claude integration (first-class)
**MCP server** (`aibroker/mcp_server.py`, stdio, Python `mcp` SDK, MIT): `list_job_types`, `submit_job`, `queue_status`, `job_status`, `job_output`, `job_history`, `wait_for_job` (blocking, max 1500 s, repeatable), `move_job`, `hold_job`, `release_job`, `cancel_job`, `resources`, `get_limits`, and the owner-only `pause_queue`, `resume_queue`, `set_playing_mode`, `set_limits`. Every tool and parameter is documented in its schema and the server sends usage instructions, so Claude needs no prior knowledge (tested with a fresh `claude -p`). **Skill** `skill/ai-broker/SKILL.md`: when to submit, how to give estimates, never start heavy jobs directly, how to be notified (`aijob wait` in the background). `register.bat` / `unregister.bat` / `mcp.json` prepare the registration; nothing edits the owner's Claude settings or any CLAUDE.md by itself.

## Independence
Own folder and repo; no imports from the games. Project-specific job types and paths live in `adapters/<name>/` (jobtypes + vars), generic ones in `jobtypes/`.

## Output folders and the two ways in
Every job gets `output/<model type>/<date>_<name>/` (ASCII slug), created by the broker, also exported as `{outdir}` / `AIBROKER_OUTDIR`; the broker writes `result.json` (job id, seconds, peaks, command) and `job.log` there. The window's main area is Models (per-type output browser with thumbnails, open folder, re-run) + Queue/History + Resources. The owner submits with a minimal dialog (type, input file or drop, name; advanced folded) and re-runs from History or from a file's menu; Claude uses MCP/CLI (`submit_job`, `rerun_job`). Both create the same job in the same queue.

## Built-in assistant (Claude inside the window)
First entry of the model list: a normal chat with Claude. Each message runs Claude Code **headless and hidden** (`claude -p --output-format stream-json --resume`, no terminal anywhere) with the broker's MCP tools and `skill/ai-broker/AGENT_PROMPT.md` (session-only flags, no settings edited; the prompt is extended with the UI language). It can read the queue, resources, history and outputs, look at the hardware (`hardware_profile`), run jobs, search the web and keep `docs/MODELS.md` / `DOWNLOADS.md`. Model: Haiku by default, Sonnet or the account default selectable. Uses the owner's Claude plan quota.

**Permissions.** Claude Code is started with `--permission-prompt-tool mcp__ai-broker__approve`, a tool that exists only for this assistant (`AIBROKER_ASSISTANT=1` in a per-turn MCP config). Whenever Claude Code would ask, the broker (`aibroker/permissions.py`) classifies the call (`safe` reads, `change` writes / downloads / installs / runs, `danger` deletes or stops programs, `blocked` formatting, registry and security settings, Claude's own settings, deleting drives or user folders) and applies the level the owner chose in the assistant header: **careful** (asks about every shell command), **normal** (default: read-only commands run, changes ask), **free** (changes run, only danger asks). `blocked` is never allowed. A question is a card in the chat (plain-language description, the raw command behind "show the command", Approve / Decline); the Claude turn waits for the click inside the same turn, so nothing is restarted. A row under the content tells the owner when the assistant page is not in front. Verified with real Claude by `tests/e2e_approval.py` (separate throw-away broker, port 47699).

## Look and feel
IDE-style dark theme (`aibroker/theme.py`: neutral greys, one blue accent, 4-6 px radii, own thin line icons drawn from an SVG set, 10 pt text with Ctrl +/- zoom) and a small design kit (`aibroker/kit.py`: tool-window headers, resource mini-gauges, status chips, the **notice bar** (messages are docked under the content, never floating over it), the model-list painter with running/waiting/result pills, the status-bar background-task indicator, a wrapping layout, the chat `MessageView` and the Ctrl+K command palette).

**Layout (space planning).** Header (state + actions, gear = Settings) / a thin resource strip (RAM, GPU, disk, CPU, the "Limits" popup with the sliders and today's numbers) / model list (narrow) + the page of the selected model (about 80 percent of the width) / the queue and history panel, which shows only its tab bar while there are no jobs and opens by itself for a job or the History tab. **Hebrew text** (`aibroker/rtltext.py`): the direction of a paragraph comes from the majority script, not the first letter; English names, numbers and paths inside Hebrew stay readable (bidi isolates for numbers with units); code stays left-to-right. Logo: three requests converge into one ring (`assets/`).

## Control
Owner: drag rows / right-click run next, up, down, pause, cancel; Pause all (queue only, or also suspend running); **I am playing / recording** toggle (no GPU starts, running GPU jobs suspended, resumes on off). `PAUSE_AI.bat` / `RESUME_AI.bat` / `PLAYING_ON.bat` / `PLAYING_OFF.bat`.

## Notification
An external process cannot message a Claude session. The requester runs `aijob wait <id> [<id>...]` as a **background command**; it polls the broker, prints one summary line (state, exit code, seconds, peak RAM) and exits (0 ok, 1 failed, 2 cancelled, 3 timeout), which wakes the agent. Optional Windows toast (`"toast": true`) and a tray balloon from the GUI.

## Logging
Per job: start/end, seconds, peak working set (polled process tree), peak commit (Windows Job Object `PeakJobMemoryUsed`), peak VRAM (PDH GPU Process Memory counter), free RAM at start. SQLite in `%LOCALAPPDATA%\ai-broker`; job output in `logs\<id>.log`.

## GUI stack
One window, Python 3.12 + **PySide6 (Qt 6, LGPL-3, used unmodified as a pip dependency, never redistributed)** + psutil (BSD). Native tray, tables with drag-drop, theming with one stylesheet, runs next to the Python job code; no Electron or web page.

**Languages.** Hebrew (default, right-to-left) and English (left-to-right), chosen in Settings (gear icon); the choice is saved in the broker's `config.json` (`lang`) and reopens the window. Every UI string in the code is a Hebrew source string wrapped in `T()` (`aibroker/i18n.py`) with the English text in `aibroker/i18n_en.py`; job types carry `he_*` and `en_*` texts. `tools/i18n_tool.py check` and `tests/test_i18n.py` keep the table complete. The in-window Claude answers in the chosen language.

## Hardware profile and the first-run setup
`aibroker/hardware.py` (daemon op `hardware`, MCP tool `hardware_profile`): GPU name and VRAM, RAM, free space on every drive, the tools the models need (Blender, ComfyUI, Python, git, ffmpeg, Claude Code), in about 0.2 s. The assistant uses it instead of shell commands, so no approval is needed to look at the machine.

**Model packs** (`catalog/packs.json`, logic in `aibroker/catalog.py`): a pack = the job types it enables, hardware needs (VRAM minimum and comfortable, RAM, disk), licence, the tools it runs on and its files. `files` have an official URL, size and SHA-256 (verified against the official file list and the copies already installed on the author's computer); `detect` only says where the files are when they were installed another way; a pack with neither is manual and is handed to Claude. The verdict (`ok` / `tight` / `no`) comes from the hardware profile, the status (`installed` / `partial` / `missing` / `unknown`) from the files' presence and size. **Setup wizard** (`SetupWizard` in `gui.py`, opened automatically only on a brand-new installation, otherwise from Settings or Ctrl+K): 1 choose categories, 2 the computer and the packs (pre-ticked: fits and not installed), 3 downloads with progress. Ticked packs become `download` jobs in the queue (`runners/download_file.py`: https from known hosts only, also after redirects; resumes `<file>.part`; keeps a file only if size and SHA-256 match; refuses when the disk is too small). Daemon ops `packs` and `install_packs`; MCP tools `list_model_packs` (read, no approval) and `install_model_pack` (asks according to the permission level). Not in the first version: LLM packs, installing ComfyUI or Python environments for the user, packs for other people's job types. Tests: `test_catalog.py`, `test_download.py` (local server), `e2e_setup.py` (separate broker), `e2e_wizard.py` (the window).

## It will NOT
Run on a network (localhost only, no auth: any process of this user can submit); kill processes it did not start; manage the game's or the owner's own programs; schedule time-of-day jobs; start itself at login unless the owner turns it on in Settings; change CLAUDE.md or any agent rules; resume a job after a *broker* crash (running jobs survive, but their exit code is then unknown -> state `lost`); give true VRAM isolation (it plans from estimates and measurements, the driver can still page).
